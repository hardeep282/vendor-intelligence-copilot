Vendor Intelligence Copilot

A multi-agent decision-support system for a beverage distributor's category, procurement and finance teams, where Python computes every number, specialist agents gather the evidence, and a single mandatory Guardian decides what the user is allowed to see.

Built by Hardeep Bamrah 10-day build sprint 531 automated tests Python · LangGraph · Anthropic API · DuckDB
Runs locally and is fully tested. Cloud deployment is the next step.
The problem

Commercial questions cut across five kinds of evidence

"Which vendors are leaking controllable margin, why, what will next quarter's demand look like, and what should we renegotiate?" Answering that means pulling figures from a 12.8-million-row SQL medallion, running a forecast, scoring SKU risk, and reading contract terms, all at once.

Doing it by hand is slow. Handing it to one LLM is worse. A single unverified agent can invent a margin figure or quote one vendor's terms in an email to another, and in a commercial setting either mistake is costly. So I built the safety into the structure of the system rather than into a prompt.

Python computes

Forecasts, risk scores, reorder points and SQL results come from deterministic tools. The LLM only narrates them.

Least privilege

Each specialist agent has its own tools and cannot call another agent's tools.

One gate to the user

Every path out of the graph passes through the Guardian. A test checks this against the compiled graph itself.

Humans approve actions

Anything that would leave the system, such as a vendor email, pauses for an approver.

    Before trusting a number

    Bugs I found in my own measurements

    A feature that rebuilt the target

    The first risk classifier scored F1 0.994. ProfitMargin, an input feature, could reconstruct the label it was predicting.

    Removed it. F1 settled at 0.919, the number I report.

    A fine-tune that never trained

    Training loss read 0.000000. A 512-token limit cut off every example's SQL answer, so the adapter learned nothing.

    Raised the limit to 1024 and retrained. Loss fell from 0.551 to 0.0006.

    A test question that saw its own answer

    Few-shot retrieval let each held-out question pick itself as its top example, which inflated the baseline.

    Excluded held-out items from the example pool before scoring.

    A scorer that marked right answers wrong

    Execution accuracy required exact column names, so a correct query with a different alias failed.

    Compared result rows instead of column labels.

    Decisions on record

    Why it's built this way

    • ADR-002 A licence-safe snapshot of vendor-level aggregates only, never committed to Git.
    • ADR-005 Direct Anthropic API rather than Bedrock, for now.
    • ADR-006 Guardian severity order: block, then escalate, then redact, then allow.
    • ADR-007 Adopt the fine-tune only after it passes a broader question set.
